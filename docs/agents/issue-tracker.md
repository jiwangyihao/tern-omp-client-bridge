# Issue tracker

Use GitHub Issues and the `gh` CLI. Infer the repository from `origin`; this
project's repository is `jiwangyihao/tern-omp-client-bridge`.

## Specifications and implementation tickets

- The authoritative product specification is a GitHub Issue, linked from README.
- Publish a complete specification as its own issue with `ready-for-agent`.
- Decompose approved specifications into self-contained tracer-bullet tickets.
  Each ticket must identify its parent specification, observable acceptance
  criteria, blocking prerequisites, and out-of-scope work.
- Record native GitHub blocking dependencies where the API supports them. If it
  does not, use an explicit **Blocked by** list of issue links and state that
  fallback; do not imply an ordinary cross-reference enforces scheduling.
- Work blockers-first. Update the issue with implementation and verification
  evidence before closing it.
- Specifications and tickets generated by this workflow are already agent-ready;
  do not send them through triage again.

## Incoming requests

Search existing issues and inspect their bodies, labels, and linked decisions
before creating duplicates. Apply the role mapping in
[triage-labels.md](triage-labels.md) to requests that arrived outside the planning
workflow.

Use body files when creating or editing substantial issue text. Keep credentials,
real device identifiers, private paths, and operational access details out of
public issues. Synthetic examples and redacted research evidence are acceptable.

PRs as a request surface: **no**.
